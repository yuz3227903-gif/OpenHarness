# Slack 式多 Agent 协作工作台 MVP 设计

## 1. 目标与范围

本轮在 `feature/bojiboji` 分支上交付一个 Windows 本地运行的浏览器协作工作台。产品采用通用多 Agent 工作台的数据和页面结构，首版只接通仓库中已有的七个投研 Agent：Planner、Fundamental、IndustryCompetition、MarketCatalyst、Risk、ReviewerArbiter 和 ReportWriter。

MVP 必须满足 PRD 的 10 条验收标准：频道消息、单个或多个 `@Agent`、真实任务执行、并行和串行协作、实时状态、成果交付与返工、消息/任务/成果/证据互相跳转、Markdown 报告生成与下载、有限失败恢复，以及前端不泄露密钥和模型隐藏思考。

本轮明确不实现：

- 多用户、登录和多工作空间隔离；
- 页面创建或测试自定义 Agent；
- 外部 Agent Gateway、Token 和心跳；
- 页面创建或导入 Skill；
- Word 报告导出；
- 将现有工作台 HTTP Server 整体迁移到 FastAPI。

这些能力属于 PRD 的 P1/P2。MVP 的数据接口和组件边界不得把它们永久写死，但不为未交付能力制作假入口。

## 2. 已选方案

采用“React 工作台重构 + 复用现有 Python 业务内核”。

- 使用 React、TypeScript 和 Vite 替换 `.openharness/plugins/investment-research/workbench/` 下的原生 HTML/CSS/JavaScript 页面。
- 保留 `openharness.invest_research.workbench_server` 作为本地 REST、SSE、静态资源和文件下载入口。
- 保留现有 SQLite 协作存储、CrewAI 编排、OpenHarness Agent 运行、证据链、正式报告和兜底报告实现。
- 通过补充稳定 API 合同连接新前端，不在本轮重写已经可运行的七 Agent 链路。

选择该方案是为了把变化集中在用户体验和 API 边界，同时降低投研执行回归风险。工作台后端未来可以迁移到 FastAPI，但迁移不属于本次 MVP 的完成条件。

## 3. 总体架构

```text
React + Vite 浏览器工作台
        |
        | REST：查询与操作
        | SSE：实时运行事件
        v
Workbench Server
        |
        +-- CollaborationStore / SQLite
        +-- 文件、交付物和 Markdown 报告
        +-- ResearchFlow / CrewAI 编排
        +-- OpenHarness 七 Agent 与工具调用
```

各单元职责如下：

- React 工作台只负责展示、用户输入、局部状态更新和导航，不自行决定任务状态。
- Workbench Server 验证请求、管理任务状态、提供资源查询和推送事件。
- CrewAI 决定串行、并行和定向返工顺序。
- OpenHarness 负责单个 Agent 的真实运行、工具和权限。
- SQLite 保存消息、线程、任务、交付物、审查问题和事件的正式记录。
- 文件系统保存上传附件、版本化成果和 Markdown 报告；数据库保存其元数据和关联 ID。

API Key、模型凭证和外部工具密钥只能由后端读取。前端只能看到“已配置/未配置”，任何 API 响应、SSE 事件或日志都不得返回完整凭证。前端展示工具名、来源、进度、结果和错误，不展示模型隐藏思考过程。

## 4. 页面结构

整体采用已确认的“Slack 主线 + 内嵌任务卡片”布局。

### 4.1 全局导航栏

最左侧窄栏提供四个实际可用入口：

- 搜索：搜索消息、Agent、任务和文件；
- 协作：频道和私信；
- 成员：Agent 目录和关系图；
- 任务：跨频道任务列表。

首版只有一个本地工作空间所有者，不显示登录入口。

### 4.2 协作侧栏

协作视图左侧显示频道和私信：

- 支持创建、进入和切换频道；
- 每个频道显示未读数量；
- 私信列出七个内置 Agent 及在线/运行状态；
- 私信只提供聊天，不展示频道级任务和文件管理。

### 4.3 频道消息主区

消息时间线是主要工作区。普通消息、系统消息、任务派发、工具调用、交付物、审查问题、返工和报告都使用明确的消息类型展示。

- 普通文本消息不会自动启动 Agent。
- `@单个 Agent` 创建一个定向任务。
- `@多个 Agent` 为各 Agent 创建独立任务，无依赖时并行执行。
- `@Planner` 在频道主时间线启动完整七 Agent 研究；在线程内提及 Planner 只创建定向补充任务，不重启整个流程。
- `@频道` 只通知成员，不自动运行所有 Agent。
- 输入 `@` 时显示 Agent 名称、职责和当前状态。
- 消息输入区提供附件、暂停/继续项目、团队人数和发送操作。
- 已触发任务的消息若编辑或撤回，必须保留修改记录；普通消息允许编辑和撤回。

任务和交付物以紧凑卡片嵌入消息流，提供“查看任务”“打开线程”“预览成果”“查看证据”等操作。

### 4.4 统一右侧抽屉

右侧区域按当前选择展示一种对象，避免用户离开频道上下文：

- 线程：根消息、回复和输入框；
- Agent：资料、动态、相关聊天和 Skills；
- 任务：目标、负责人、依赖、状态、时间和关联交付物；
- 交付物：摘要、版本、提交者、审查状态、预览和下载；
- 证据链：Source → Fact → Logic/Risk → Review → Report；
- 报告：Markdown 预览、下载和证据编号跳转。

抽屉可关闭。关闭后主消息区扩展，不保留遮挡内容的空白列。

### 4.5 成员页

成员页包含七 Agent 目录和关系图。

- Agent 卡片展示头像、名称、Agent ID、内置类型、职责、模型、工具、频道和状态。
- 关系图以频道内历史 `@` 和任务交接为边，显示 Agent 间实际发生过的联系。
- 图下显示 Agent 数量、连接数量和连接最多的 Agent。
- Agent 详情使用资料、动态、聊天、Skills 四个标签页。
- Skills 标签只展示已有 Skill；MVP 不提供创建或导入操作。

### 4.6 任务页与搜索

任务页按“待开始、进行中、待审查、需返工、已完成、失败、已取消”筛选，展示负责人、依赖、所属频道和交付物数量。任务状态由后端统一更新，Agent 不能自行把任务标记为已完成。

统一搜索支持关键词和类型筛选，结果覆盖消息、Agent、任务和文件，并可跳回原频道、线程或详情对象。MVP 不实现复杂搜索语法。

## 5. 数据对象与接口边界

MVP 使用以下稳定对象：

- `Channel`：频道名称、描述、成员和未读状态；
- `Message`：作者、类型、正文、提及、附件、线程、修改历史和时间；
- `Thread`：根消息及回复集合；
- `Agent`：身份、类型、职责、模型、工具、状态和频道；
- `Task`：目标、创建者、负责人、输入、预期交付、依赖、状态和时间；
- `Artifact`：名称、摘要、类型、版本、任务、提交 Agent、证据编号和审查状态；
- `ReviewIssue`：严重程度、问题、责任 Agent、返工要求和状态；
- `Source/Fact/Logic`：证据链节点及所属任务、频道和权限；
- `Report`：Run、Markdown 路径、生成方式和下载信息；
- `RunEvent`：事件 ID、序号、时间、频道、Agent、任务、类型、状态和安全载荷。

前端使用 REST 完成查询与命令，使用一个按频道订阅的 SSE 流接收状态变化。SSE 事件至少覆盖：

- `message_created`；
- `task_started`、`task_updated`、`task_failed`；
- `agent_running`；
- `tool_called`；
- `artifact_submitted`；
- `review_requested`；
- `report_generated`。

事件必须包含单调递增游标。浏览器断线重连时提交最后游标，后端从 SQLite 补发遗漏事件。前端按事件 ID 去重并局部更新，不通过重复刷新整个快照模拟实时性。

## 6. 核心协作流程

1. 用户在频道或线程发送消息并提及一个或多个 Agent。
2. 后端持久化消息，解析提及，并为每个被触发 Agent 创建唯一任务。
3. 无依赖任务并行执行；有依赖任务等待前置交付物。
4. Agent 状态变为运行中，后端通过 SSE 推送阶段、工具和错误事件。
5. Agent 完成后提交版本化 Artifact，并在原频道或线程创建交付卡片。
6. Reviewer 针对事实、来源或逻辑创建 ReviewIssue；返工只创建责任 Agent 的补充任务。
7. 新版本 Artifact 保留旧版本，Reviewer 复审后关闭问题或保留警告。
8. ReportWriter 只使用登记且已审查的交付物生成 Markdown 报告。
9. 用户从报告编号逐级跳转至逻辑、事实和原始来源。

后续 Agent 读取正式 Artifact 和当前任务材料，不默认读取其他 Agent 的全部聊天历史。

## 7. 状态、异常与降级

任务状态固定为：待开始、进行中、待审查、需返工、已完成、失败、已取消。暂停项目不等于失败：运行中的工作在安全检查点停下，新任务不再启动；继续后恢复未完成队列。

- 网络或模型临时失败自动重试一次，重试事件对用户可见。
- Agent 返回空内容或格式错误时只修复一次，仍失败则记录失败。
- 单个 Agent 失败不取消无依赖的其他任务。
- Agent 超时后终止当前调用，任务进入失败状态。
- 用户取消运行后，所有未启动任务进入已取消；已产生的消息和成果保留。
- SSE 断开时前端退避重连，并从最后事件游标恢复。
- 页面刷新或服务重启后，从 SQLite 恢复已有消息、任务、成果和事件。
- Reviewer 的普通问题达到返工上限后，以“待验证事项”进入报告，不无限阻塞。
- ReportWriter 失败时生成明确标记的本地兜底报告；页面不得把兜底报告显示为正式成功。

所有重试、错误、取消、降级和权限拒绝都写入可审计事件。

## 8. 前端组件边界

React 前端按职责拆分：

- `AppShell`：全局布局与当前导航；
- `WorkspaceRail`：搜索、协作、成员、任务入口；
- `ConversationSidebar`：频道、私信、未读状态；
- `ChannelHeader`：频道信息、团队人数和运行控制；
- `MessageTimeline`：按消息类型选择渲染器；
- `Composer`：文本、附件、提及菜单和发送状态；
- `TaskCard`、`ArtifactCard`、`ReviewCard`、`RunEventRow`：消息流中的结构化事件；
- `ContextDrawer`：线程、Agent、任务、成果、证据和报告详情容器；
- `MembersView` 与 `AgentGraph`：目录与关系图；
- `TasksView`：任务筛选与列表；
- `SearchView`：统一搜索与跳转；
- `api`：REST 客户端、错误归一化和请求类型；
- `events`：SSE 连接、游标恢复、去重和状态归并。

组件不得直接拼接后端 URL 或自行解释原始数据库字段；所有转换集中在类型化 API 层。

## 9. 测试策略

### 9.1 前端测试

- 组件测试覆盖消息类型、任务卡、成果卡、抽屉、提及菜单、加载、空状态和错误状态。
- 状态测试覆盖 SSE 事件顺序、重复事件去重、断线游标恢复和局部更新。
- 浏览器流程覆盖创建/进入频道、发送普通消息、`@Agent`、多 Agent、打开线程、查看任务、预览交付物和下载报告。

### 9.2 后端测试

- API 合同测试覆盖频道、消息、线程、Agent、任务、交付物、搜索、运行控制和报告。
- SQLite 测试覆盖刷新恢复、消息修改历史、Artifact 版本和证据关联。
- SSE 测试覆盖首次连接、心跳、游标补发、断线和事件安全载荷。
- 编排回归测试覆盖单 Agent、并行 Agent、依赖等待、定向返工、失败重试和兜底报告。

### 9.3 最终验收

在 Windows 本地环境中，用浏览器完整运行：

1. 创建或进入频道并发送普通消息；
2. 分别触发单 Agent、多 Agent 和完整 Planner 流程；
3. 观察并行、串行、工具调用和失败状态的实时更新；
4. 打开线程并发起一次定向返工；
5. 在消息、任务、成果、证据和报告之间跳转；
6. 预览并下载 Markdown 报告；
7. 刷新页面后确认正式记录仍存在；
8. 检查浏览器响应、SSE 和日志不含 API Key 或隐藏思考。

只有上述流程和 PRD 的 10 条 MVP 验收标准全部通过，才视为完成。
